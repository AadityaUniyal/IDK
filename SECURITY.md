# TRACE Security Policy

## Secret boundary

Provider keys, Neon connection strings, authentication secrets, and session material are server-only. They belong in encrypted deployment variables or an ignored `frontend/.env.local` file.

Never:

- Put `DATABASE_URL`, `GEMINI_API_KEY`, or `GROQ_API_KEY` in client components.
- Prefix private credentials with `NEXT_PUBLIC_`.
- Commit `.env.local`, cookies, logs, database dumps, screenshots, or terminal transcripts.
- Return provider errors, SQL errors, connection strings, or tokens to the browser.
- Copy credentials into README files, issues, pull requests, or generated artifacts.

## Before publishing

1. Run `git status --short` and inspect the full diff.
2. Search the repository for `DATABASE_URL`, `GEMINI_API_KEY`, `GROQ_API_KEY`, `postgres://`, `postgresql://`, `AIza`, and `gsk_`.
3. Confirm `.env.local` and generated files are ignored.
4. Rotate any credential that was ever exposed outside the encrypted environment.
5. Run `cd frontend; npm run build`.

## Runtime controls

- Authentication uses scrypt password hashes and SHA-256 session token hashes.
- Server-side policy evaluation gates writes, external calls, and destructive actions.
- Tool inputs generated by models are schema-validated before execution.
- External page fetching rejects private-network and metadata hosts, uses a timeout, disables redirects, and enforces a response-size limit.
- Mission step leases reduce duplicate execution from concurrent browser tabs or retries.
- Neon foreign keys, indexes, and database checks protect persistence integrity.

## Reporting

If you find a security issue, do not include secrets or personal data in a public issue. Revoke exposed credentials immediately, preserve a minimal reproduction, and report the issue privately to the project owner.
